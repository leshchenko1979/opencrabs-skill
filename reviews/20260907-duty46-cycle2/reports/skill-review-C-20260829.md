**1. supervisor.md §Duty 5 / §Duty 7 · "`the Supervisor issues BINDING rulings, each logged as an event entry in `workers-ledger.json` (`rulings`) with evidence and reasoning.`" (supervisor.md:129-130) · "`2. INBOX = the ledger: on receipt the Supervisor stamps an `idea` event into`" + "`3. Same-turn ACK to the sender, then triage; the verdict is stamped as an `idea-verdict` ledger event:`" (supervisor.md:204-205, 207-208) · "`stamp ONE ledger event (version published, no per-worker notify rows), then`" (supervisor.md:81) · dimension: ledger-event stamping (state-file sealing family) · problem: four duties (1/3/5/7) each require appending a row to `workers-ledger.json` `events[]` with the n-sequence + flock + atomic-tmp->mv discipline — yet the ONLY existing writer is oc-deploy's in-file `ledger_stamp()` (oc-deploy:134-147), reachable only on the swap path for kind=`swap-result`. There is no standalone CLI for the supervisor's own `skill-bump`/`rulings`/`idea`/`idea-verdict` stamps, so every one is a hand jq append against the same live file the 2026-08-29 deletion incident (ledger event 1303) taught to never hand-edit. · fix: **`tools/oc-ledger stamp <kind> "<what>" [--by <label>] [--ledger <f>]`** — flock'd, `n = max(.events[].n)+1`, append `{n,t,by,what,kind}`, atomic tmp->mv, `jq -e` post-write validate, exit-coded (0 ok / 2 bad-kind-or-ledger / 3 write-fail), sources `lib/oc-log.sh` · severity: **HIGH**.

**2. workers-ledger.json §meta / SKILL.md §frontmatter · "`"current_skill_version": "0.4.37",`" (workers-ledger.json:4) vs "`"current_skill_version": "0.4.39",`" (workers-ledger.json:474) vs "`"skill_version": "0.4.39"`" (workers-ledger.json:502) · ledger event 1304: "`Meta sync: current_skill_version and skill_version 0.4.38 -> 0.4.39 in this write.`" (workers-ledger.json:1082) · "`version: 0.4.39`" (SKILL.md:11) · dimension: version-bump paperwork / state consistency (checksum-class) · problem: one release must keep three version fields in agreement — SKILL.md frontmatter line 11 plus two (actually three, counting meta duplicates) ledger fields — and the hand ritual ALREADY dropped one: the top-level field reads 0.4.37 while both meta fields and SKILL.md read 0.4.39, two bumps after a claimed sync. Worse, this intra-ledger skew is invisible to the one checker that exists: oc-skew-scan derives "current" only from `SKILL="/root/.opencrabs/profiles/ops/skills/opencrabs-dev/SKILL.md"` + `CURRENT="$(sed -n 's/^version:[[:space:]]*//p' "$SKILL" ...)"` (oc-skew-scan:74-75) — it never reads the ledger's own version fields. · fix: **`tools/oc-ledger sync --version <v> [--why <provenance>]`** — one flock'd atomic write sets top-level `current_skill_version` + `meta.current_skill_version` + `meta.skill_version` AND appends the `skill-bump` event (provenance in `what`) in a single tmp->mv; plus read-only **`oc-ledger check-version`** that exits 1 when any of the three fields disagrees with SKILL.md `version:` — the drift above would fail loudly, not ship silently · severity: **HIGH**.

**3. supervisor.md §Duty 4 / §Duty 6 · "`Cadence: STANDING — after every FIVE shipped version bumps (shared trigger with Duty 6), on owner request, or when incidents cluster without a rule.`" (supervisor.md:111-112) · "`Cadence: after every FIVE shipped version bumps, on owner request, or when an incident suggests drift.`" (supervisor.md:141) · dimension: standing-cadence trigger · problem: when to fire Duty-4 poll and Duty-6 review is a "five shipped version bumps" counter shared by two duties, but nothing computes it — the supervisor must manually count `skill-bump` kind events in `events[]` at each bump (or miss the trigger; it shares the hand-hidden state of finding 2). · fix: **`oc-ledger cadence`** (read-only subcommand) — counts `skill-bump` rows since the newest `skill-review-*`/`review-battery` stamp, prints "N/5", exits 0 WAIT / 1 FIRE; printed automatically by `oc-ledger sync` after each bump so the shared trigger surfaces at the moment it can fire · severity: **MED**.

**4. supervisor.md §Duty 6 · "`3. PERSISTENCE (added after two report losses to bounces, 2026-08-26): the Supervisor persists each returned report to `/tmp/skill-review-<lens>-<YYYYMMDD>.md` on receipt (read-only reviewers cannot write); a report existing only in push-transit does not count as delivered.`" (supervisor.md:179) · dimension: Duty-6 report persistence (receipt delivery class) · problem: a standing policy (fires on the duty-6 cadence) executed as a raw file-write whose naming+date convention lives in memory; two reports were already lost to bounces before the step was added, and "persisted vs still-in-transit" is a manual judgment every time. · fix: **`tools/oc-review-persist <lens> <text-or-file> [--dir /tmp]`** — writes `/tmp/skill-review-<lens>-<YYYYMMDD>.md` (same-day idempotent), appends a receipt row (path+sha256+ts) to `/tmp/skill-review-index.log`, and exits 0 only when the file is re-read on disk after write — so a "delivered" claim is never made from transit alone · severity: **MED**.

**5. supervisor.md §Duty 2 · "`- **Ack contract (decision 3):** a worker acks with a one-line `ACK <version>` at its next turn boundary after notification.`" (supervisor.md:67-68) · dimension: roster/registry write on delivery · problem: every ACK needs a nested worker-row rewrite (`last_acked {version, at}`) plus an ack event row — the same hand-jq family as finding 1, recurring per worker per version, on the same live ledger the 2026-08-29 incident restricted to tool-only writes. · fix: **`oc-ledger ack <uuid> <version> [--at <ISO|HH:MMZ>]`** — validates full-uuid + `N.N` version shape, sets `.workers[] | select(.uuid==$u) | .last_acked={version,at}`, appends the `ack` event, same flock + tmp->mv + validate discipline · severity: **LOW**.
